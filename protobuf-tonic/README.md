# protobuf-tonic

`protobuf-tonic` lets Tonic services use `pbrs` message types instead of Prost messages. It is for Rust developers who want the Tonic 0.14 ecosystem with Google protobuf v4 application traits. The crate is preview software at `0.1.0-alpha.2` and older Tonic versions are unsupported.

> ⚠️ **Pre-Release Notice**: `protobuf-tonic` is currently in **preview / pre-release (`0.1.0-alpha.2`)** and is **not yet production ready**.
>
> ### Known Gaps & Roadmap (TBD)
> - **OK-Path Custom Trailers**: Tonic 0.14 does not expose custom trailers on successful responses (`Response` lacks a `trailers()` accessor); custom trailing metadata is only delivered on error statuses.
> - **Tonic Ecosystem Trait Boundaries**: `pbrs` message types implement Google protobuf v4 application traits (`Parse` / `Serialize`), not `prost::Message`. Existing middleware or tower layers expecting `prost::Message` are incompatible.
> - **Version Support**: Strictly targets Tonic 0.14+. Older versions (0.12, 0.13) are unsupported.

## What it is

`protobuf-tonic` is a [tonic 0.14+](https://crates.io/crates/tonic) `Codec`
adapter plus generated client and server stubs for `pbrs` message types
(`Parse` / `Serialize`).

Use it when you want standard Tonic transport, middleware, and Tower layers,
but you want protobuf messages generated by `pbrs`.

## How it differs from nearby crates

| Choice | Use it when | Important boundary |
|---|---|---|
| `protobuf-tonic` | You want Tonic 0.14+ with `pbrs` messages. | Messages implement `Parse` / `Serialize`, not `prost::Message`. |
| `tonic-prost` | You want the default Tonic + Prost stack. | It expects Prost message types. |
| [`pbrs-grpc`](../pbrs-grpc) | You want a lightweight pure-Rust HTTP/2 gRPC kernel without Tonic or Tower. | It is a separate gRPC stack, not a Tonic codec. |

The `pbrs` protobuf kernel has no `tonic`, `hyper`, or `tower` dependency.
`protobuf-tonic` is the adapter layer that connects it to the Tonic ecosystem.
MSRV is 1.88.

## Usage

### 1. Add dependencies

```toml
[dependencies]
tonic = { version = "0.14", default-features = false, features = ["transport", "codegen", "router"] }
pbrs = "0.2"
protobuf-tonic = "0.1.0-alpha.2"
http = "1"
tokio-stream = "0.1"
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }

[build-dependencies]
pbrs = "0.2"
```

`protobuf-tonic` is published as a preview crate. From `0.1.0-alpha.2` on it
builds from a checked descriptor set without `protoc`; the older
`0.1.0-alpha.1` archive still needs it.

The `compile_protos` example below still needs `protoc` for your application's
`.proto` files. For a cold build without `protoc`, use
[`Config::compile_descriptor_set`](../docs/guides/codegen.md#generating-from-a-checked-descriptor-set)
with a previously compiled, checked descriptor set.

### 2. Generate Tonic stubs (`build.rs`)

Default `compile_protos` emits native `pbrs-grpc` kernel stubs. Tonic users
must opt in with `emit_tonic_stubs(true)`. Generated messages implement
`Parse` / `Serialize`, not `prost::Message`.

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    pbrs::codegen::Config::new()
        .emit_tonic_stubs(true)
        .compile_protos(&["proto/hello.proto"], &["proto"])?;
    Ok(())
}
```

The generator emits `FooClient`, `FooServer`, and the `Foo` service trait using
`ProtobufCodec` instead of Prost.

### 3. Implement a service

```rust
use tonic::{Request, Response, Status};
use helloworld::{Greeter, GreeterServer, HelloRequest, HelloReply};

struct MyGreeter;

#[tonic::async_trait]
impl Greeter for MyGreeter {
    async fn say_hello(
        &self,
        request: Request<HelloRequest>,
    ) -> Result<Response<HelloReply>, Status> {
        let mut reply = HelloReply::new();
        reply.set_message(format!("Hello, {}!", request.get_ref().name()));
        Ok(Response::new(reply))
    }
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let addr = "127.0.0.1:50051".parse()?;
    tonic::transport::Server::builder()
        .add_service(GreeterServer::new(MyGreeter))
        .serve(addr)
        .await?;
    Ok(())
}
```

### 4. Call the service

```rust
use tonic::Request;
use helloworld::{GreeterClient, HelloRequest};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut client = GreeterClient::connect("http://127.0.0.1:50051").await?;

    let mut req = HelloRequest::new();
    req.set_name("World");

    let response = client.say_hello(Request::new(req)).await?;
    println!("Response: {}", response.into_inner().message());

    Ok(())
}
```

## Supported features

| Feature | Status |
|---|---|
| RPC shapes | Unary, client-streaming, server-streaming, and bidirectional streaming. |
| Compression | `send_compressed` and `accept_compressed` for Gzip. |
| Interceptors | Request and response interception through Tonic's `with_interceptor`. |
| Message size limits | `max_decoding_message_size` and `max_encoding_message_size`. |
| Health and reflection | Works with `tonic-health` and `tonic-reflection`. |
| Trailers and status | HTTP/2 headers and status trailers are supported. Tonic 0.14 still lacks an OK-path custom trailer accessor on `Response`. |

## Performance vs Prost

Benchmarks live in `tonic-bench`; see [`docs/benchmarks.md`](../docs/benchmarks.md).

- **Unary `rpc_mixed`**: about 2x the throughput of Prost.
- **Large payloads (`name_4kib`)**: faster than Prost for combined encode/decode.
- **Sparse messages and dense tags**: regression tests gate decoding speed against the target thresholds.
