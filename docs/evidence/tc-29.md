# TC-29: unmodified tonic-generated clients on pbrs transport

TC-29 adds an opt-in HTTP transport implementation for `pbrs_grpc::Channel`
using the existing `tonic` feature. No shipping manifest, default feature,
dependency version or lockfile changes are required. A generated
`RouteGuideClient::new(channel)` or `RouteGuideClient::with_interceptor(channel,
interceptor)` accepts the native channel directly. Its generated source is
the ordinary output of the existing standalone fixture's tonic-prost-build
0.14.6 pipeline; no generated client is edited.

## Transport and policy boundary

The adapter opens a stream on the existing native pool, including resolver
selection, ring-hash request metadata, client-side health checking,
least-request in-flight tracking, TLS, reconnects, channel authority and
HTTP/2 configuration. It streams tonic's preframed `Bytes` through the
existing transport seam. Incoming DATA and trailers pass through an
`http_body::Body`; flow-control credit is returned when DATA is handed to
tonic. Terminal status is also reported to the channel's outlier policy.

Channel RPC concurrency is enforced before dispatch. The tighter of a
`grpc-timeout` request header and the channel timeout covers pool acquisition,
response headers and the response body. An upload task observes cancellation
and the deadline even when its producer is idle or its response body is not
being polled. Dropping the call before headers, or the response afterwards,
cancels that task and resets its stream. The response retains its connection,
idle lease and least-request load guard through termination.

Tonic owns protobuf encoding/decoding, compression, generated interceptor
execution and message limits. Applying the native typed-call policy API to
an opaque compressed HTTP body would bypass its contract. The adapter
therefore returns `FAILED_PRECONDITION` before dispatch for native request or
response interceptors, binary logging, finite transport-byte budgets, custom
native message/compression settings, or a matching method service-config
entry. Configure these on the generated tonic client or Tower layers.
`max_send_buffer_size` also installs a native finite byte budget, so that
combined configuration is rejected as well. The adapter does not silently
drop that budget to apply its HTTP/2 send-buffer setting.
Native per-call telemetry and retry accounting are not emitted by this
adapter; pool acquisition still uses the configured observer. Native
typed-call retry/hedge policies are not applied to opaque, potentially live
request streams.

The standalone interop manifest enables only the existing `tonic` feature.
Its lockfile adds three feature-unified edges between packages already
present (`pbrs-grpc -> tonic`, `tonic -> tokio-rustls`, `rustls -> log`),
without adding any package or changing a version/checksum.

## Copy costs and performance acceptance

There is no payload decode/re-encode, body collection, in-memory HTTP/2
bridge or payload copy in this adapter. The upload path uses
`wire::send::send_bytes`, whose chunk splits share the original `Bytes`
allocation. The response returns each transport DATA `Bytes` unchanged.
The implementation adds one forwarding task per HTTP request, a boxed
service future, cancellation/error signaling and a boxed response body;
request metadata is cloned for LB hash selection. These are costs that
require measurement.

There is an upstream codec difference from native prost stubs. Tonic 0.14.6
`codec/decode.rs::StreamingInner::poll_frame` calls
`self.buf.put(frame.into_data().unwrap())`, copying received DATA into its
`BytesMut` decoding buffer. Native `codec::pop_from_chunk` slices a complete
uncompressed frame without this copy. That tonic codec behavior remains
unchanged on this transport, and gzip still requires decompression. Keeping
unmodified tonic-generated code does not turn tonic's decoder into the
native codec.

The current SB-26 harness explicitly excludes TC-29/TC-30 and implements
handwritten typed client/server profiles. Its recorded `native_prost`
results do **not** qualify this adapter. The unmodified tonic-codegen
profile must be added with the frozen SB-26 corpora and equivalent handlers,
then measured against tonic's Channel with the unchanged collector/control
rules. TC-29's performance acceptance remains open; no speed or leadership
claim follows from the integration tests or source-level copy inspection.

## Validation

The source commit is `98e79816a874dd5a449b9c86c13509f899695274`, based on
`cf3eee22c6b06324e299f81b76915651471d8025`. These local gates ran on the
exact source/test bytes in that commit, before committing. The integration
tests cover all
four TC-22 RouteGuide call shapes against both original tonic and native
servers, generated interceptors, gzip, message limits, initial/trailing
metadata, status details, deadlines, resolver-managed channels and an idle
bidirectional producer. The kernel tests cover opaque wire-byte/trailer
preservation, policy rejection before peer invocation, native concurrency
permit release, cancellation before headers, response drop and deadline
reset without polling a response body.

| Existing hostile peers / retry safety / tonic server / typed Tower | 40 / 18 / 2 / 7 passed |
| Strict scoped kernel Clippy and standalone all-target Clippy | Passed with `-D warnings` |
| Tonic-feature rustdoc | Passed with `RUSTDOCFLAGS=-Dwarnings` |
| Feature-off compile and normal dependency tree | Passed; tree excludes tonic, Tower and hyper |
| Scoped formatting / diff whitespace | Passed |

The active-uploader early-rejection regression waits for the 2 MiB upload
body to be dropped after the peer closes its receive half without refreshing
its 64 KiB window. It then polls the response, ensuring the queued upload
failure cannot hide ordinary initial headers plus non-OK terminal trailers.
The peer's status, percent-encoded message, details and metadata survive.
Another generated-client test starts a live bidirectional stream, receives
one reply, then exceeds its encoder cap; the true local `OUT_OF_RANGE`
survives the reset after response headers.

The source does not add `unsafe`. The unchanged shipping graph and the
scoped gates establish compatibility of this opt-in integration, not a
whole-workspace CI result or production soak. Raw commands, results, tool
pins and file hashes are in [validation.json](tc-29/validation.json), with
the complete stdout/stderr logs beside it. Rust/Cargo were 1.99.0;
the existing genuine pinned protoc was 35.1, tonic and tonic-prost-build
0.14.6, and prost 0.14.4. The source was independently inspected by GN-12,
whose terminal-status race finding is covered by the regression above.
