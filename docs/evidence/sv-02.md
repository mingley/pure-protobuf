# SV-02: remove redundant per-RPC server allocations

## Hypothesis

The server allocated two objects on the hot successful RPC path that were not
semantically needed:

1. `incoming_rpc` built every `Rpc` with a fresh default
   `ByteBudgetTracker`, and both `Single` and `Router` immediately overwrote it
   with the real server tracker.
2. successful unary and streaming responses built an OK `Status` detail block
   to attach empty trailing metadata before encoding the standard OK trailers.

Removing both should reduce exact heap allocations per RPC while preserving
interceptor-visible request context, metadata, byte-budget semantics, and wire
trailers.

## Change

- Added `Dispatch::byte_budget()` and implemented it for `Single` and `Router`.
- `serve_io` now clones the real dispatch byte-budget tracker before spawning
  the RPC task and passes it into `incoming_rpc`.
- Removed the later `rpc.byte_budget = ...` overwrite in both dispatchers.
- `send_unary_response` and `send_stream_response` now allocate status detail
  storage only when successful response trailers are nonempty.

No public API changed.

## Allocation evidence

Dev-loop reports are:

- Before: `target/sv-server/devloop-sv01-base.json`
- After: `target/sv-server/devloop-sv02-trailers.json`

| cell | allocs/op before | allocs/op after | delta | bytes/op before | bytes/op after | delta |
|---|---:|---:|---:|---:|---:|---:|
| `rpc.pbrs.unary` | 57.335 | 55.340 | -1.995 (-3.5%) | 55,059 | 54,804 | -256 |
| `rpc.pbrs.server_stream` | 74.335 | 72.335 | -2.000 (-2.7%) | 65,963 | 65,811 | -152 |
| `rpc.pbrs.unary_compressed` | 87.345 | 85.335 | -2.010 (-2.3%) | 1,483,557 | 1,483,300 | -257 |
| `rpc.pbrs.server_stream_compressed` | 937.415 | 937.270 | -0.145 | 25,084,169 | 25,096,385 | +12,216 |

The compressed server-stream cell is dominated by gzip internals and shows
allocation jitter; the targeted unary and uncompressed stream cells clear the
2% dev-loop allocation win bar.

Wall time on this host was noisy and is not used as evidence.
