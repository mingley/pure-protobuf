# RX-08 Tokio scheduling and wakeup cost

Date: 2026-09-28/29. Base SHA: `a09b26c3d...` at worktree creation
(`origin/main` after H2-01). Host: Apple M4 Pro, macOS, shared/contended.
Linux instruction counts were collected inside the repository dev-loop
container on arm64 Linux with valgrind/callgrind. Wall-time and context-switch
counts are **dev-loop, contended host** diagnostics.

## Verdict

**No production-code change was kept.** RX-08 confirmed H2-01's read: the
closed-loop dev-loop RPC cells spend most measured instructions in Tokio and
runtime wake/park machinery, but the scoped safe candidates tested here did
**not** reach the >=2% dev-loop win rule on both unary and streaming cells.

The main actionable result is attribution and rejection of two low-risk ideas:

- avoid client queue-wait timestamp reads when no lifecycle observer is
  installed;
- avoid no-op per-attempt telemetry guard/timestamp work when no lifecycle
  observer is installed;
- avoid the extra `yield_now` batching turn for short stream bursts.

The best combined candidate improved Linux callgrind IR by only **0.64%** on
unary and **1.86%** on server-streaming, with no allocation win and worse/noisy
macOS context-switch proxy results. It was reverted.

## Important harness boundary

The dev-loop RPC cells run both client and server in **one Tokio multi-thread
runtime**:

```rust
tokio::runtime::Builder::new_multi_thread().enable_all().build()
```

Inside the cell, the server is spawned into the same runtime and the client
drives closed-loop requests over loopback. This is useful for deterministic
relative counts, but it inflates cross-task parking/wakeup costs compared with a
deployment where client and server run in separate processes and often on
separate hosts. Do not treat the absolute Tokio share as production CPU share.

## Call-site attribution

Manual callgrind captures for `rpc.pbrs.unary` and
`rpc.pbrs.server_stream` were collected with:

```sh
valgrind --tool=callgrind --cache-sim=no \
  --callgrind-out-file=target/rx-08/manual/callgrind.baseline.<cell>.out \
  bench/devloop/target/release/devloop run-cell <cell> --iters 120 --warmup 20
```

The inclusive callgraph confirms that pbrs-grpc repeatedly enters Tokio and h2
through these hot surfaces:

| Area | Evidence from callgrind callgraph | Notes |
|---|---|---|
| Server accept -> per-RPC task spawn | `server::connection::serve_io_in` accepts each stream, builds `Rpc`, then `R::spawn(async move { dispatch.dispatch(...).await })` | Safe removal is SV-03/RX-08's hard part. Polling arbitrary user futures inline can head-of-line block the connection task. |
| Client connection driver task | `client::pool::finish_h2` and `ClientConnection<TcpStream>::poll` appear under Tokio task polling | This is per-connection, not per-RPC, but the dev-loop co-locates it with every RPC. |
| Cancellation watch channel | `Call` creates a `watch::channel(false)` per RPC; `first_of`, send, and response races clone/await receivers | Public `Call::cancel`/`CallHandle` semantics depend on this. A new primitive would require `request.rs`, outside this card's write scope. |
| Server-stream parked send half | `wire::send::reset_on_cancel` spawns a task holding `SendStream` after request half-close | Needed so a `CallHandle` can still reset a live server-stream/bidi stream after headers; avoiding it safely needs a new cancellation owner design. |
| Application stream channel | `Streaming::channel` uses bounded `tokio::mpsc` for application-produced response streams | `recv_many` batching reduces writes, but small streams still cross channel/wake boundaries. |
| Batching yield | `let_producer_catch_up()` uses `tokio::task::yield_now()` when a producer is ahead of the network | Helps bulk streams; adds a scheduler turn for small response bursts. Candidate tested and rejected below. |
| Deadlines/timers | `first_of`/`race` create a timer only when a deadline exists; no timer registration is used for `None` in the core unary/server-stream path | The "avoid no-deadline timer" idea was already implemented for these paths. |

## Candidate experiments

All candidates were measured on the same two Linux dev-loop cells. They are
listed here because RX-08 asked for testing ideas independently and keeping only
wins.

| Candidate | Change | Unary IR | Server-stream IR | Allocations | Decision |
|---|---|---:|---:|---:|---|
| Queue timestamp fast path | Compute `tokio::time::Instant::now()` for client queue wait only when an observer exists | -0.26% | -1.29% | unchanged / tiny jitter | Rejected: below 2%. |
| Attempt telemetry fast path | Add a no-observer `MaybeAttemptGuard` to skip attempt labels/start timestamp/no-op guard work | -0.80% | -1.13% | bytes -0.15% / -0.12%, alloc count unchanged | Rejected: below 2%. |
| Short-burst yield threshold | Avoid `yield_now` for stream batches smaller than 8 messages, combined with the attempt fast path | -0.64% | -1.86% | bytes -0.15% / -0.12%, alloc count unchanged | Rejected: still below 2%; context-switch proxy worsened under host noise. |

The candidate context-switch proxy did not improve:

| Cell | Baseline invol ctx/RPC | Combined candidate invol ctx/RPC | Baseline Mach msg/RPC | Candidate Mach msg/RPC |
|---|---:|---:|---:|---:|
| unary | 6.28 | 7.73 | 5.95 | 5.64 |
| server-stream | 14.54 | 15.46 | 7.71 | 7.56 |

Because no candidate cleared the win rule, the production-code changes were
reverted before committing this evidence.

## What not to change casually

- **Per-RPC server spawn:** likely real overhead, but unsafe to remove by
  simply polling handler futures on the connection task. A correct experiment
  needs a cooperative budget and a head-of-line blocking regression where one
  slow handler cannot stall new streams on the same connection.
- **`reset_on_cancel` task:** removing it changes post-headers `CallHandle`
  cancellation unless the parked `SendStream` gets a new owner that can reset
  immediately without polling the response stream.
- **`watch::channel` per call:** public `Call::cancel`, `CallHandle`, drop
  cancellation, deadline races, and streaming reset semantics all currently use
  it. Replacing it needs a request/call cancellation primitive design outside
  this card's write scope.
- **`let_producer_catch_up`:** short streams may dislike the scheduler turn,
  but it exists to batch bulk streams and halve writes/wakeups. Any threshold
  change needs both small-stream and bulk-stream cells.

## Follow-up design

The next RX card should be an explicit cancellation/runtime redesign rather
than more local micro-edits:

1. Introduce a crate-private cancellation primitive that lets a `CallHandle`
   reset a parked send half directly, without a per-RPC watch receiver and
   `reset_on_cancel` task.
2. Add dev-loop cells for client-streaming and bidi upload/ping-pong with
   instruction and context-switch counters, because CL-05 already showed those
   are worse relative to tonic than unary.
3. Prototype one-poll inline server dispatch behind a test-only gate with:
   - a Tokio cooperative budget;
   - a slow-handler HOL regression on one connection with concurrent streams;
   - RT-07 overload and RT-08 drain tests.
4. Add exact Linux context-switch/wakeup counters or `perf sched` evidence on a
   dedicated host; `/usr/bin/time -l` on macOS is only a proxy.
