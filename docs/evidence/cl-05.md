# CL-05 streaming pump assessment

Date: 2026-09-28. Baseline artifacts:
[`client-profiles.md`](client-profiles.md),
`target/client-perf/rpc-bench-go-upload.json`, and
`target/client-perf/rpc-bench-fallback-ping_pong.json`.

## Current state

`pbrs-grpc/src/client/streaming.rs` has two different outbound streaming
implementations:

- Client-streaming (`run_client_stream`) already keeps the send half on the
  call future stack and drives `pump_outbound_budget` in the same `select!` as
  the response future. This matches the CL-05 direction and is why dropping the
  call can reset the send half reliably.
- Bidi (`run_bidi`) still spawns an outbound pump task and coordinates
  `StreamSender::fail` through two `oneshot` channels so a pre-headers failure
  surfaces as the sender's `Status` instead of an h2 reset status.

## Evidence

Go independent-server diagnostics:

| Shape | Native client | Tonic-pbrs client | Read |
|---|---:|---:|---|
| client-stream upload | 424.5 us client CPU/RPC, 34.4k msgs/s best line | 392.2 us client CPU/RPC, 50.6k msgs/s best line | Tonic leads; client-stream still has room even without a spawned task. |
| bidi ping-pong fallback | 1,105-1,132 us client CPU/RPC | 1,004-1,060 us client CPU/RPC | Tonic leads; the spawned bidi pump and two oneshots are plausible costs. |

The current dev-loop harness has no client-streaming or bidi cell, so there is
no exact task-spawn/allocation primary for CL-05. Shipping a rewrite would rely
on rpc-bench wall/CPU diagnostics only, which does not satisfy the fleet perf
rules.

## Why no code shipped

Removing the bidi pump safely is not a local substitution. The returned
`StreamSender` currently owns an `mpsc::Sender`; the pump task owns the
HTTP/2 `SendStream`, batches outbound messages, holds byte-budget permits,
handles `StreamSender::fail`, and keeps the send half alive after the `Call`
has returned response headers. A no-pump design needs a new sender backend that
can own or share the `SendStream` directly while preserving:

- pre-headers `StreamSender::fail` status precedence over h2 reset errors;
- cancellation/deadline resets before and after response headers;
- drop behavior when either `Call`, `StreamSender`, or received `Streaming` is
  dropped first;
- byte-budget and channelz accounting currently centralized in
  `pump_outbound_budget`;
- batching fairness from `OutBatch::BURST` and `let_producer_catch_up`.

That crosses enough semantics that it needs a dedicated design/test patch plus
a dev-loop C3 cell that counts bidi spawns/allocations. No CL-05 code was
shipped in this pass.

## Follow-up proposal

Split CL-05 into:

1. Add dev-loop `rpc.pbrs.client_stream` and `rpc.pbrs.bidi_ping_pong` cells
   that report task spawns (or an internal spawn counter), allocations and
   bytes.
2. Introduce an internal `StreamSender` backend enum:
   `Channel(mpsc::Sender<...>)` for server-produced/application streams and
   `DirectClient { send, budget, wire, cancel }` for client request streams.
3. Port bidi only after client-streaming/direct-send tests prove
   `fail`, cancellation, deadline, drop and reset behavior unchanged.
