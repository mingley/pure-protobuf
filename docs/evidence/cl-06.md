# CL-06 cold-start and client-memory verdict

Date: 2026-09-28. Depends on [SB-12](sb-12.md).

## Hypothesis

CL-06 asked for lower time-to-first-RPC and lower per-channel/per-stream memory.
The plausible implementation levers are DNS/TCP/TLS setup and HTTP/2
preface/SETTINGS pipelining.

## Evidence

SB-12 scale rows show:

| Metric | pbrs-grpc | tonic | Verdict |
|---|---:|---:|---|
| 1k idle bytes/connection median | 84,263 | 93,143 | pbrs already wins memory. |
| 1k bytes/open stream median | 14,942 | 20,939 | pbrs already wins memory. |
| 1k first empty unary RPC median | 2.280 ms | 1.760 ms | pbrs loses cold start. |
| 10k idle bytes/connection | 81,229 | 91,070 | pbrs wins memory in a limit probe. |
| native TLS first RPC | 4.949 ms | not run | no tonic TLS row in pure-Rust harness. |

## Implementation verdict

No CL-06 code shipped in this pass.

Within the assigned code scope (`pbrs-grpc/src/client/channel.rs` and
`pbrs-grpc/src/tcp.rs`), there was no measured client-memory win to take:
pbrs-grpc already uses less RSS per idle connection and per open stream in the
available scale rows.

The cold-start loss is not addressable in those two files without crossing the
assigned boundaries. The relevant code is currently in `pbrs-grpc/src/client/pool.rs`:

- `handshake_io` dials TCP/TLS and then calls `finish_h2`;
- `finish_h2` intentionally drives the h2 connection until
  `current_max_send_streams() > 0`, i.e. until peer SETTINGS are applied;
- pipelining the first request before that wait would require changing the
  pool/transport handshake path and proving lazy-connect, wait-for-ready,
  deadline, cancellation and stream-cap semantics unchanged.

That overlaps the client pool/transport surfaces touched by CL-04/RX/H2 work,
not the allowed CL-06 write scope for this request. Shipping a speculative
change in `tcp.rs` alone (for example replacing `TcpStream::connect` with a
`TcpSocket` path) would not target the measured cold-start bottleneck and would
need new cross-platform source-bind/proxy proof.

## Follow-up

Create a focused CL-06b/H2 follow-up that owns `client/pool.rs` or the transport
seam and measures:

1. first-RPC with current SETTINGS wait vs first request pipelined after client
   preface where the HTTP/2/gRPC semantics allow it;
2. lazy-connect and wait-for-ready deadlines/cancellation under the pipelined
   path;
3. peer `MAX_CONCURRENT_STREAMS=0/1` SETTINGS behavior before and after the
   first request;
4. dev-loop Linux instruction counts and `rpc-bench scale` first-RPC medians.

## 2026-09-29 pass (base `ff7b30e9`, branch `mingley/cl06-cold-start`)

Independent second attempt, same verdict. Code changed: two regression tests
in `pbrs-grpc/src/tcp.rs` (bound-literal family-mismatch error, no-proxy-env
direct dial); production code byte-identical to base. `channel.rs` untouched:
`Target::parse` runs once per channel construction (never per RPC),
`Channel` carries 15 bytes of padding (reorder saves nothing observable),
and every constructor delegates dialing to `pool`, so no per-connect heap
in this file's code paths could be removed.

Dial fast paths (IP-literal DNS skip, proxy-env gate) were implemented,
measured, and reverted: `tokio::net::lookup_host` on an IP literal costs
~125 ns (std already fast-paths literals; `localhost` costs ~137 us), and
the proxy-config parse allocates nothing when variables are absent, so the
combined saving was ~0.2 us per dial — 0.05% of a ~440 us connect, below
significance in an interleaved A/B (refused-dial p50s identical at n=2000).
The kept tests lock the error/proxy semantics a future fast path must
preserve. Env caching was rejected: proxy tests mutate env per case, and
per-dial consultation is the documented contract.

C6/C7 were measured with a throwaway release harness (native
`GreeterServer`, fresh connect + one unary per iteration, native vs tonic
interleaved ABBA; loopback macOS, diagnostic tier). SB-12 scenarios could
not show client work: their opener is Python `ssl`, so client-side cells
were required.

| Cell | pbrs-grpc | tonic | Note |
|---|---:|---:|---|
| Held-connection bytes/conn (500 held, 3 rounds) | 83,722 / 83,788 / 83,788 | 104,366 / 104,366 / 104,104 | native wins ~20%; same-process, same native server, so the delta is the client |
| Dial-to-first-RPC p50 (n=400 x3) | 682–777 us | 621–739 us | native loses ~40–60 us |
| Connect-only p50 | 441–479 us | 249–359 us | gap is the SETTINGS wait (see below) |
| Refused-dial p50 (n=2000) | 65–71 us | 63–69 us | dial-path CPU at parity |

Attribution (public-API split, `Channel::from_io` vs tonic connector):
native H2+build p50 ~223 us vs tonic ~51 us. The ~170 us is
`pool::finish_h2` waiting for peer SETTINGS before `connect` returns; tonic
returns after flushing its preface. For dial-to-first-RPC totals that wait
is neutral (tonic pays it inside its first-RPC leg instead), leaving a
~40 us pure-RPC-leg gap in `call.rs` (concurrent worker's scope) plus
~20 us of pool-side connect build (channelz, slots, h2 buffers). No part
of either gap is reachable from `channel.rs`/`tcp.rs`.

Dev-loop compare (`rpc.pbrs.unary`, `rpc.tonic.unary`, pinned protoc 35.1):
base vs dial-change trees identical (56.33/56.33 and 71.33/71.32 allocs
per RPC) — the dial runs outside the measurement window, so the cells are
a no-regression check, not an improvement proof. Touched-path health:
lib 423, TLS 22, proxy 7, codegen lazy/wait-for-ready 26, all green;
`cargo clippy --all-targets --all-features -- -D warnings` and
`cargo fmt --check` clean.

Per-accept verdicts: C6 beats tonic (pre-existing win, unchanged by this
pass) but does not improve; C7 neither improves (below significance) nor
beats tonic; lazy-connect and wait-for-ready semantics unchanged (proven
by the existing client/channel tests above). The 09-28 follow-up stands:
C7 needs the CL-06b pool/transport pipelining pass, and the ~40 us RPC-leg
gap belongs to the `call.rs` worker.
