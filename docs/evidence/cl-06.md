# CL-06 cold-start and client-memory verdict

Date: 2026-09-28. Depends on [SB-12](sb-12.md).

## Hypothesis

CL-06 asked for lower time-to-first-RPC and lower per-channel/per-stream memory.
The plausible implementation levers are DNS/TCP/TLS setup and HTTP/2
preface/SETTINGS pipelining.

## Evidence

SB-12 scale rows show:

| Metric | pbrs-grpc | tonic | Verdict |
|---|---:|---:|---|
| 1k idle bytes/connection median | 84,263 | 93,143 | pbrs already wins memory. |
| 1k bytes/open stream median | 14,942 | 20,939 | pbrs already wins memory. |
| 1k first empty unary RPC median | 2.280 ms | 1.760 ms | pbrs loses cold start. |
| 10k idle bytes/connection | 81,229 | 91,070 | pbrs wins memory in a limit probe. |
| native TLS first RPC | 4.949 ms | not run | no tonic TLS row in pure-Rust harness. |

## Implementation verdict

No CL-06 code shipped in this pass.

Within the assigned code scope (`pbrs-grpc/src/client/channel.rs` and
`pbrs-grpc/src/tcp.rs`), there was no measured client-memory win to take:
pbrs-grpc already uses less RSS per idle connection and per open stream in the
available scale rows.

The cold-start loss is not addressable in those two files without crossing the
assigned boundaries. The relevant code is currently in `pbrs-grpc/src/client/pool.rs`:

- `handshake_io` dials TCP/TLS and then calls `finish_h2`;
- `finish_h2` intentionally drives the h2 connection until
  `current_max_send_streams() > 0`, i.e. until peer SETTINGS are applied;
- pipelining the first request before that wait would require changing the
  pool/transport handshake path and proving lazy-connect, wait-for-ready,
  deadline, cancellation and stream-cap semantics unchanged.

That overlaps the client pool/transport surfaces touched by CL-04/RX/H2 work,
not the allowed CL-06 write scope for this request. Shipping a speculative
change in `tcp.rs` alone (for example replacing `TcpStream::connect` with a
`TcpSocket` path) would not target the measured cold-start bottleneck and would
need new cross-platform source-bind/proxy proof.

## Follow-up

Create a focused CL-06b/H2 follow-up that owns `client/pool.rs` or the transport
seam and measures:

1. first-RPC with current SETTINGS wait vs first request pipelined after client
   preface where the HTTP/2/gRPC semantics allow it;
2. lazy-connect and wait-for-ready deadlines/cancellation under the pipelined
   path;
3. peer `MAX_CONCURRENT_STREAMS=0/1` SETTINGS behavior before and after the
   first request;
4. dev-loop Linux instruction counts and `rpc-bench scale` first-RPC medians.
