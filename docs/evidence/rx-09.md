# RX-09 per-RPC instruction and allocation measurements

Date: 2026-09-29. Status: **in progress; not a qualified performance win**.
This is an evidence-only measurement of committed code, not a new optimization.

## Verdict

Against the pre-RX-09 source, native unary and server-streaming median Callgrind
instructions fell **9.33% and 8.58%**, and allocated bytes fell **19.07% and
15.93%**, respectively. Allocation counts were essentially unchanged.

The requested beat-tonic gate is **not met**: native server-streaming still has
**3.38% more instructions** in the original dev-loop cells. Moreover, those
cells do not do equivalent work: native streaming returns 1 KiB per RPC while
tonic returns 4 KiB, with different codecs and handlers. The cross-stack table
below is diagnostic, not a fair transport or application comparison.

No separate-process endpoint CPU/RPC, matched-offered-load p99, TLS on/off,
mixed traffic, or retained-byte profile was collected. RX-09 remains open.

## Method and workload boundaries

Built each exact source with `CARGO_BUILD_JOBS=2`, `cargo build --locked
--offline --release --manifest-path bench/devloop/Cargo.toml`. Source and pinned
protobuf mounts were read-only. Cached Cargo/target volumes were reused. The
baseline build and captures finished before rebuilding the current binary.
The cached pinned `protoc` directory was placed first on build `PATH` because
the v4 fixture build invokes `protoc` directly.

Each source ran four unmodified cells, three repetitions per cell, paired
200- and 400-RPC processes: **24 captures per source, 48 total**. For each:

```sh
valgrind --tool=callgrind --cache-sim=no \
  --callgrind-out-file=/out/callgrind/<cell>.repeat<N>.n<iters>.out \
  /build/release/devloop run-cell <cell> --iters <200-or-400> --prepare-iters 400
```

This uses the same differential algorithm as `devloop run`:
`IR/RPC = (IR(400) - IR(200)) / 200`, then median of three pairs. Both whole
process totals include setup, one connection-settling warmup RPC and teardown;
differencing approximates removal of fixed costs, rather than instrumenting
only the measured loop. `--prepare-iters` is relevant to codec cells, not these
RPC cells. Allocation count/bytes are the N=200 child's armed allocation-window
totals divided by 200, then median; reallocations count as allocations and add
the requested new size. These are allocated bytes, **not retained memory**.

The [capture script](rx-09/capture.sh) preserves the individual child JSON,
stderr and complete Callgrind profiles which the normal aggregator discards.
The [summarizer](rx-09/summarize.py) requires all expected files, one correctly
identified child result per process, empty stdout, valid allocation counters,
and agreement between every profile's `summary` and stderr's `I refs` total.
All 48 captures passed. Every sample is retained in
[results.json](rx-09/results.json), including raw wall counters only for audit;
no wall-time claim is made.

All cells are plaintext, uncompressed, concurrency-one closed-loop loopback,
with client and server inside one multi-thread Tokio runtime/process. Fixed
cell order is native unary, tonic unary, native stream, tonic stream; repeats
are not randomized. Callgrind counts instructions, but runtime scheduling can
still vary the execution path. Ranges below expose that variation; three
repeats are not confidence intervals or dedicated-host qualification.

| Original cell | Codec/service and handler | Request application payload | Responses per RPC |
|---|---|---:|---:|
| Native unary | pbrs Greeter, owned string conversion/echo | 1,024 B | 1 × 1,024 B |
| Tonic unary | prost Echo, move request bytes into reply | 1,024 B | 1 × 1,024 B |
| Native server-stream | pbrs Greeter, split comma-separated string | 1,027 B | 4 × 256 B = 1,024 B |
| Tonic server-stream | prost Echo, clone payload for each reply | 1,024 B plus `replies=4` field | 4 × 1,024 B = 4,096 B |

The source already warns that these differing services/codecs do not isolate
transport. SB-01's separate `rpc-bench` repair does not qualify these cells.
The [benchmark contract](../benchmark-contract.md), especially §§2, 5.4 and
10, still applies. The matched Echo/prost dev-loop cells described in
[TC-03](tc-03-prost.md) are a possible next diagnostic, not a substitute for
RX-09's separate-process qualification.

The unchanged tonic control illustrates execution-path variation; do not
attribute its small changes to native transport work. The native instruction
ranges do not overlap their respective baseline ranges in this run, and the
roughly 10.4 KiB/RPC byte reduction is stable across all samples. This supports
a development-loop improvement, not a production speed or resource claim.

## Retained evidence and validation

Each archive contains 24 raw Callgrind profiles, 24 stderr files, 24 stdout
files, successful build/capture logs, and compiler/binary provenance:

- [Baseline raw captures](rx-09/baseline-6cbf19e9.tar.gz), 2,671,350 bytes.
- [Current raw captures](rx-09/current-9a04f82b.tar.gz), 2,655,471 bytes.
- [All samples, hashes and calculated deltas](rx-09/results.json).
- [Exact commands and provenance](rx-09/provenance.json).

Recompute after extracting the archives into a fresh directory:

```sh
python3 docs/evidence/rx-09/summarize.py <extracted>/baseline <extracted>/current
```

Archive extraction and this recomputation reproduced `results.json` byte for
byte (SHA-256 `7ae9886311e3e4ae4582ed99cc5f89491ae0d30b4263242478fa522ee45c4764`).
Archive/file hashes, expected 75 files per archive, shell syntax, source
cleanliness and evidence whitespace were checked. Both release builds and all
48 profiled children exited successfully. No production or harness source was
edited for this measurement.

This pass does **not** claim new exact-`9a04f82b` transport-CI qualification.
Earlier correctness evidence remains in [shared-map recovery](shared-map-recovery.md)
and the RX-09 task's `b158cc99` test record; neither substitutes for the open
performance acceptance work. `perf`/`strace` are absent from the image, so
hardware instructions, syscall/futex counters, endpoint CPU/RPC, p99 at matched
offered load, retained bytes, TLS and mixed separate-process traffic are
explicitly **not run** here.

Next required work: make the cross-stack application work comparable, close
the remaining streaming instruction gap without weakening transport gates,
then profile the merged candidate in separate Linux client/server processes
with TLS on/off and mixed unary/streaming traffic. Shared-runtime Tokio counts
must not be promoted to production endpoint CPU attribution.
