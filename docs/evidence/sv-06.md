# SV-06: bounded streaming batch experiment

## Hypothesis

Increasing stream batch byte and message bounds might reduce write wakeups for
bulk server-streaming responses without changing call semantics.

Experiment:

- `STREAM_BATCH_BYTES`: 32 KiB -> 64 KiB.
- `OutBatch::BURST`: 64 -> 128 messages.

Both changes were local-only and reverted after measurement.

## Method

Baseline report:

- `target/sv-server/devloop-sv05-immediate-errors.json`

Experiment report:

- `target/sv-server/devloop-sv06-batch64k128.json`

Cells:

- `rpc.pbrs.server_stream`
- `rpc.pbrs.server_stream_compressed`

Host label: dev-loop, contended macOS host. Allocation counts are the primary
signal; wall time is not used for the decision.

## Results

| cell | allocs/op baseline | allocs/op experiment | bytes/op baseline | bytes/op experiment | verdict |
|---|---:|---:|---:|---:|---|
| `rpc.pbrs.server_stream` | 70.335 | 70.335 | 65,749.5 | 70,869.5 | worse bytes |
| `rpc.pbrs.server_stream_compressed` | 935.855 | 935.140 | 25,099,727.6 | 25,100,426.8 | no material win |

## Verdict

Rejected. The larger batch bounds did not remove allocations and made the
uncompressed dev-loop cell allocate about 7.8% more bytes/op. The current
32 KiB / 64-message bounds remain in place.

## Follow-up

Future SV-06 work should target a cell with more messages per RPC than the
current dev-loop `server_stream` cell or add a dedicated measured cell before
changing production batch bounds. A change should include explicit latency and
fairness evidence for request/response streams so interactive streams do not
pay for bulk throughput.
