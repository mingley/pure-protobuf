# SV-05: static trailers and trailers-only error responses

## Hypothesis

The server already uses trailers-only responses for immediate errors, but the
successful OK path still paid for constructing an empty status detail block
before sending static OK trailers. Skipping that allocation should reduce the
common path while preserving gRPC wire behavior.

## Change and verdict

Implemented as part of the SV-02 allocation patch:

- `send_unary_response` and `send_stream_response` keep `Status::ok()` as a
  code-only status when response trailers are empty.
- Nonempty OK trailers still allocate and attach to `Status` exactly as before.
- Immediate errors continue to use `send_trailers_only` / `reject`, so their
  trailers-only wire behavior is unchanged.

Follow-up in `server/connection.rs` adds the remaining immediate server-side
deadline case:

- if `grpc-timeout` plus the server overlay is already zero before dispatch,
  the connection task returns `DEADLINE_EXCEEDED` as a trailers-only response
  without taking an RPC slot, spawning a handler task, or reading the body.

This completes the measured local OK-trailer allocation win and the immediate
UNIMPLEMENTED / RESOURCE_EXHAUSTED / pre-dispatch DEADLINE_EXCEEDED
trailers-only coverage. No additional static `HeaderMap` cache was added
because h2 consumes an owned `HeaderMap`.

  - `immediate_unimplemented_is_trailers_only`;

  Each verifies HTTP 200, `grpc-status` in the initial headers, no DATA frames,
  and no separate trailing trailers.

## Limits

This is dev-loop evidence on a shared macOS host. grpc-go/C++ peer interop was
not rerun locally; raw HTTP/2 tests prove the trailers-only wire shape.
