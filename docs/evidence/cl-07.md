# CL-07: preface pipelining conflicts with the current connection contract

The default client remains unchanged. On source
`cf3eee22c6b06324e299f81b76915651471d8025`, HTTP/2 already supports sending
the first request before receiving peer SETTINGS, but native channels
deliberately wait. Bypassing that wait violates documented eager-connect,
stream-admission and cold-handshake retry behavior. This is a negative
correctness investigation, not a cold-start performance improvement. CL-07's
cold/TLS P4 acceptance remains unqualified.

## Premise and boundary

[CL-06](cl-06.md) identified the SETTINGS wait and separated its cost from
end-to-end first-RPC latency. [SB-12](sb-12.md) retained shared-host scale
diagnostics and did not run the tonic TLS comparison. Neither artifact proves
that removing the wait preserves the current API contract.

The locked `h2` dependency is 0.4.19, registry archive SHA-256
`ef8e5e5a340588f4452631496976cf8636d4a7ecf600239fdc27615d2530bc16`.
Its `client::handshake2` writes the client connection preface, buffers initial
SETTINGS, and returns without reading peer SETTINGS. Its default initial send
budget is `usize::MAX`; `SendRequest::ready` does not independently await the
peer preface. The dedicated raw-peer test confirms that this API sends
HEADERS while the peer has sent no bytes. RFC 9113 permits this sequence; no
new HTTP/2 implementation is needed to enable it.

Native `ChannelConfig::h2_builder` instead sets `initial_max_send_streams(0)`.
`client::pool::finish_h2` drives the connection until the peer applies a
positive send-stream limit. This establishes three existing guarantees:

- `Channel::connect` and `Channel::from_io` wait for the peer preface, and
  `connect_timeout` includes that wait. A socket accepted by a silent peer
  does not become a successfully connected channel.
- A zero peer stream cap waits; a cap of one serializes competing requests.
  The first RPC does not use an assumed positive peer allowance.
- A failed cold handshake stays before request dispatch. Wait-for-ready can
  retry that failure without treating already-transmitted request data as
  an uncommitted dial failure.

`h2` documents that streams exceeding a subsequently received peer limit
can receive `PROTOCOL_ERROR` or `REFUSED_STREAM`. Starting with a budget of
one reduces speculation but cannot preserve a peer's zero-stream allowance.
Separating eager connect from lazy acquisition would preserve only the eager
contract; the lazy first request would still change stream admission and
the point at which a failed attempt can be retried.

## Controlled rejection

The dedicated [cl07_preface.rs](../../pbrs-grpc/tests/cl07_preface.rs) contains
ten behavioral tests. The unmodified baseline passed all ten
([raw log](cl-07/baseline.log)). A temporary
[diagnostic patch](cl-07/rejected-diagnostic.patch) overrode the initial send
budget to one inside `finish_h2`. It did not change the connection driver,
timeouts, retry code, TLS, framing, or any threshold. The existing readiness
check then treated provisional capacity as successful peer SETTINGS.

That diagnostic exited 101: two tests passed and eight failed
([raw log](cl-07/rejected-diagnostic.log)). In particular, eager connect
returned `Ok` for a silent peer, cold requests emitted HEADERS before
admission, and the closed-handshake wait-for-ready fixture no longer retried.
This is a rejected semantic counterexample, not a measured optimization
candidate. The patch was restored byte-for-byte before running any final
gates, and no shipping source changes are retained.

The retained tests cover:

| Behavior | Wire-level assertion |
|---|---|
| Existing h2 pipelining capability | First HEADERS precedes every peer byte. |
| Eager connect and peer cap zero | No successful connect before SETTINGS; cap zero waits until a later cap of one. |
| Silent-peer connect timeout | `UNAVAILABLE` and transport EOF. |
| Eager handshake cancellation | Aborting the unfinished connect drops the transport. |
| Lazy connect and cold cancellation | No socket until the RPC is polled; aborting its handshake closes that socket. |
| First-RPC deadline | `DEADLINE_EXCEEDED` and transport EOF before SETTINGS, with and without wait-for-ready. |
| Lazy first-request stream admission | No HEADERS before SETTINGS or while cap is zero; cap one releases stream 1. |
| Peer cap one | Stream 3 waits until cancellation releases stream 1. |
| Wait-for-ready handshake retry | A closed cold handshake redials; the new peer must admit the first stream. |

Paused Tokio time controls the duplex-I/O tests. TCP tests use bounded quiet
intervals solely as behavioral assertions. Raw test-run durations are
incidental shared-host diagnostics and are not first-RPC measurements.

## Validation and limits

Environment:

```sh
source /workspace/pure-protobuf/work/toolchain/env.sh
export CARGO_BUILD_JOBS=1
export CARGO_TARGET_DIR=/workspace/scratch/work/cl07/target
```

The restored source passed all 101 tests in:

```sh
cargo test --locked -p pbrs-grpc --test cl07_preface --test rpc --test gaps \
  --test hostile --test message_size --test tls -- --test-threads=1
```

[Raw gate log](cl-07/restored-gates.log): CL-07 10, RPC 12, gaps 6, hostile 40,
message size 7, TLS 26; zero failures, ignored tests, or exclusions. The TLS
suite includes wrong trust/name, missing mTLS identity, required h2, and
redial checks. These are local semantic gates, not independent peer or
claim-grade performance qualification.

Scoped strict Clippy and package formatting also passed (exit zero):

```sh
cargo clippy --locked -p pbrs-grpc --lib --test cl07_preface -- -D warnings
cargo fmt --package pbrs-grpc -- --check
```

The [Clippy log](cl-07/clippy.log), [format log](cl-07/format.log), and
[artifact pins](cl-07/pins.json) retain the results and source/tool hashes.

No dev-loop baseline/after JSON, flamegraph, instruction or allocation
comparison, cold scale run, or TLS latency comparison was performed. There
is no retained runtime optimization to qualify, and the semantic
counterexample fails before performance acceptance. Limits, lazy connect,
wait-for-ready, deadlines, cancellation, security policies, dependencies and
benchmark thresholds are unchanged. The target used 787 MiB after these
gates and Clippy, below the assigned 2 GiB limit.

An explicit opt-in would need a separate reviewed contract: eager-connect
readiness and silent-peer timeout, provisional stream allowance including
zero-cap peers, retry commitment, and teardown while SETTINGS is still
pending. This investigation does not introduce that API or claim its
performance. The coordinator must keep CL-07 open until an approved safe
design and matched cold/TLS P4 evidence satisfy the original acceptance.
