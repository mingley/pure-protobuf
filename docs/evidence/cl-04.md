# CL-04 direct pool picking

Date: 2026-09-28. Base SHA for this worktree:
`349c00f1c13a9f75e736b9ef3c939a9bb8023797`.

## Hypothesis

The direct `ChannelConfig::connections` pool chose slots round-robin and only
learned about peer `SETTINGS_MAX_CONCURRENT_STREAMS` by waiting inside
`SendRequest::ready`. Under high concurrency this can keep sending work to a
connection that is already at the peer stream cap while another connection is
available.

## Change

For direct connection pools only (not resolver-managed LB policies):

- add per-slot atomic in-flight counters and the most recently observed peer
  send-stream cap;
- pick the least-loaded slot whose in-flight count is below that cap;
- fall back to the least-loaded slot when every slot is saturated, preserving
  h2's correct wait behavior;
- keep `pick_first`, `round_robin`, WRR, ring hash, least-request, priority,
  subset and outlier-detection policy selection unchanged.

This is a bounded A105 step: it respects peer stream caps when choosing among
existing direct-pool connections. It does not dynamically grow the immutable
slot vector beyond `ChannelConfig::connections`; doing that requires a separate
pool storage redesign.

## Evidence

### Deterministic dev-loop

The current dev-loop harness has no multi-connection/multi-task RPC client
cell. I ran the Linux/valgrind wrapper on the existing unary cell as a
single-connection regression proxy:

```sh
CARGO_BUILD_JOBS=3 ./scripts/devloop-linux.sh \
  --cells rpc.pbrs.unary \
  --repeats 1 \
  --iters 1000 \
  --out target/cl04-tc19/devloop-linux-baseline-unary.json

CARGO_BUILD_JOBS=3 ./scripts/devloop-linux.sh \
  --cells rpc.pbrs.unary \
  --baseline target/cl04-tc19/devloop-linux-baseline-unary.json \
  --repeats 1 \
  --iters 1000 \
  --out target/cl04-tc19/devloop-linux-after-unary.json
```

| Cell | Instructions/RPC before | Instructions/RPC after | Allocations/RPC before | Allocations/RPC after | Verdict |
|---|---:|---:|---:|---:|---|
| `rpc.pbrs.unary` | 142,377.920 | 142,207.975 | 35.010 | 35.010 | No single-connection instruction/alloc regression. |

### QPS diagnostic, concurrency 100

Command for both runs:

```sh
CARGO_BUILD_JOBS=3 ./scripts/grpc-qps-interop.sh \
  --mode=native_pair \
  --scenario=protobuf_unary_qps_unconstrained_100rpcs \
  --warmup=0 \
  --duration=1 \
  --log-dir target/cl04-tc19/qps-{baseline,after}
```

| Run | QPS | p50 | p99 | Client CPU | Server CPU |
|---|---:|---:|---:|---:|---:|
| baseline | 19,992.1 | 4,044.8 us | 18,778.1 us | 62.3% | 73.5% |
| after | 25,910.0 | 3,697.4 us | 8,226.5 us | 80.7% | 92.1% |

Verdict: the high-concurrency native-pair diagnostic improves QPS by 29.6% and
tail latency by 56.2% on this contended host. This is diagnostic wall/QPS
evidence, not claim-grade; the primary deterministic coverage is limited by the
missing multi-connection dev-loop cell.

## Tests

Added `connection_pool_spreads_when_peer_stream_cap_is_low` in
`pbrs-grpc/tests/rpc.rs`: a four-connection client pool sends 16 concurrent
unary RPCs to a server advertising one concurrent stream per connection; all
responses must complete with the expected labels.

## Follow-up

- Add a dev-loop cell for multi-connection, multi-task unary RPCs (for example
  `rpc.pbrs.unary_pool_concurrency_64`) so CL-04 can be gated on deterministic
  instruction counts directly.
- A full A105 pool-growth implementation needs a growable slot table; the
  current direct pool stores slots in an immutable vector sized by
  `ChannelConfig::connections`.
