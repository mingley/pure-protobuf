# gRPC execution and ownership

The goal is lower total work for clients, servers and generated code while
preserving gRPC behavior and finite resource limits. The current stack does not
yet establish that advantage over tonic/prost across the required workloads.

Rebuilding a layer is useful when it removes an identified cost or correctness
problem. Rust's ownership, static dispatch and asynchronous futures make those
designs possible; using them does not by itself make an implementation faster.

## Start with the work an RPC requires

An RPC pays connection and call setup costs, per-message work, per-byte work,
and queueing or contention. Different workloads expose different terms:

| Workload | Costs to isolate |
|---|---|
| Small unary calls | Dispatch, future allocation, metadata, locks and wakeups |
| Many idle streams plus active calls | Polls of idle handlers, cancellation registration and fairness |
| Large compressed messages | Decoder work, capacity growth, copies and retained memory |
| Read-all nested messages | Validation, materialization, repeated parsing and reference counts |
| Many generated services | Generated bytes, compiler work, future sizes and executable size |

Use equal handler work and the same codec to isolate a transport comparison.
A full interop handler and a minimal echo handler are different workloads.
Count allocations and requested bytes separately; neither measures retained
memory or establishes latency or throughput.

## Execution follows readiness and ownership

One stream becoming ready should not poll every idle stream. The server's
admitted handlers use a wake-indexed set on their connection task. The set
stores concrete dispatch futures rather than separately boxed trait objects.
Cancelling one call likewise needs its own wake registration.

Cancellation belongs to the runtime that owns the call. A process-wide parker
must not send a second runtime's work to the first runtime that registered.
Runtime-tagged, bounded thread caches and bounded registration queues keep the
common path on a shared driver. Evicted drivers drain existing registrations;
queue saturation falls back to an owned task rather than losing cancellation.
These bounds do not replace connection and RPC admission limits.
Stable runtime IDs require Tokio 1.49 or newer; the default Rust minimum remains
1.85, with the optional Zstd feature retaining its separate higher minimum.

Inline handler execution avoids a task handoff on each call. It also means
that synchronous handler or decoder work occupies the connection's task while
it runs. A wake-indexed set fixes scanning; it does not make CPU-heavy handlers
parallel or preemptible. Compare a bounded worker execution policy using mixed
idle/active streams before changing the default. Preserve reset handling,
deadlines, backpressure, drain and task-count recovery in that comparison.

## Decode once and validate the complete payload

A gRPC frame boundary and a compression member boundary are different things.
All legal gzip members or Zstd frames inside one payload contribute bytes to
one protobuf message. Validate later checksums and trailers too. Deflate carries
one zlib stream; reject bytes outside it. Apply one aggregate decoded-output
limit, with separate admission of each Zstd history window.
Count members and frames too: empty members can repeatedly reset a decoder
without consuming the output budget. The default per-message limit is 1,024
gzip members or Zstd frames, including skippable frames; deflate uses one.
`MessageLimits::with_max_compression_frames` adjusts that work limit. Lifting
only the decoded-size limit preserves it; trusted-input callers can explicitly
lift the frame limit separately.

The opaque tonic adapter must pass the complete validated message to generated
tonic code. Validating and discarding decoded bytes, then replaying compressed
input for a second decompression, duplicates work and can preserve upstream
first-member-only behavior. Normalize gzip to uncompressed-flag-zero messages,
with bounded input/output polling and the effective message cap. Identity input
can continue sharing its original byte views.

Grow output from observed decoded data. A short tail beyond 64 KiB should not
automatically reserve 128 KiB. A bounded stack lookahead can establish the tail
length before reserving it, while full chunks retain geometric growth. Do not
trust a remote size trailer to choose an unrestricted allocation. Keep exact-cap
EOF/overflow probes and checksum validation.

Output size, decoder history, block buffers, retained wire input and compressor
workspaces are separate resource costs. Bound and measure each. Reusing a
workspace per stream may save allocations while multiplying idle memory; it
needs a budget and recovery evidence. Finite input also does not make a
synchronous decompressor preemptible. Repeated small frames and advertised
history windows need adversarial work-amplification checks.

Zstd scratch is reused within one message, then released. This removes repeated
entropy-table allocation across its frames. Backend reset may reserve history
even for empty frames, and capacity growth can exceed the logical window size.
The advertised-window cap is not a total allocation or RSS cap.

## Generate the work the selected method needs

Choose the method before allocating its erased dispatch future. Boxing an
entire service's async match makes a small unary call carry the largest
method's state. Native and prost-generated services should both box the chosen
method and retain identical request/response conversions and error behavior.

Message representation needs a separate choice. Lazy views suit sparse access;
read-all handlers can pay for validation and then parse the same nested bytes
again during materialization. The next experiment is an explicit eager owned
decode path for recursive/read-all messages, compared with the existing lazy
path on both sparse and read-all corpora. Keep unknown fields, merge semantics,
extension behavior and malformed-input rejection identical.

Removing repeated validation requires a typed proof that a span was validated
under the relevant schema and limits. A raw `Wire` value is not that proof.
Do not create an unchecked fast path from caller-supplied bytes. Include
retention and reference-count work when evaluating borrowed representations.

## Replace backends when the evidence justifies it

Keep protobuf, transport, execution and optional compatibility adapters separate.
Resolver and policy updates should publish snapshots outside the call's data
path. Optional telemetry and middleware should have explicit costs.

A custom HTTP/2 engine or io_uring backend remains an experiment, not a shortcut
around scheduling, ownership or compression costs above it. Public send/receive
handles can cross tasks, so an engine with one connection owner still needs
safe commands and backpressure. Measure locks, syscalls, TLS records and copies
before choosing that boundary. The existing [HTTP/2 design](pbrs-h2.md) retains
its acceptance criteria. Another wire protocol needs its own compatibility
profile; it does not replace HTTP/2 gRPC interoperability.
