# PK-05: Hybrid table-driven parse design

Date: 2026-09-29  
Status: accepted design for follow-up implementation cards  
Scope: pbrs generated owned-message parse path

## Decision

Use a hybrid parser:

1. **Keep inline specialized parsing for small hot messages.** Messages with a
   small field set and mostly scalar/string fields continue to use generated
   `match (field_number, wire_type)` code. This preserves the current tiny
   `empty`, `id`, and short-string performance envelope and avoids adding a
   table lookup to the most latency-sensitive rows.
2. **Use compact static field tables for wide/cold messages.** Wide messages,
   repeated/map-heavy messages, and generated code whose parse body would be
   large use a shared generic loop driven by one static table per message.
3. **Share table metadata with later size/encode and UK-kernel work.** The
   first implementation uses tables only for parsing. The table layout must be
   append-only so PK-08/UK convergence can add size/encode handlers without
   regenerating incompatible metadata.

Implementation status at the 2026-09-29 audit: PK-06 supplies the safe
runtime engine in `src/table.rs`, and PK-18 uses a cached table for dynamic
messages. Generated messages still use inline parsing. PK-07 must emit the
tables and selection controls, prove semantic parity, and meet the budgets
below before generated services can benefit.

## Field-table shape

Each generated message gets a `&'static [FieldEntry]` sorted by field number:

```rust
pub struct FieldEntry {
    pub number: u32,
    pub expected_wire: u8,
    pub kind: FieldKind,
    pub storage: StorageSlot,
    pub presence: PresenceSlot,
    pub flags: FieldFlags,
}
```

Planned enums are POD-like and `Copy`:

- `FieldKind`: scalar varint/fixed32/fixed64, string, bytes, message, group,
  map entry, packed scalar, enum, oneof arm.
- `StorageSlot`: generated field offset/slot identifier, not a raw pointer in
  the first safe implementation.
- `PresenceSlot`: implicit, optional, oneof case, proto2 required bit, or none.
- `FieldFlags`: UTF-8 validation mode, packed/unpacked acceptance, repeated,
  map key/value shape, lazy-message eligibility, unknown-enum behavior.

Dispatch starts with binary search for cold tables. If measurement shows wide
messages are still branch-bound, add a generated side index:

- for dense field numbers: `first_number + small u16 index table`;
- for sparse messages: two-level `number % N` bucket table;
- fallback: sorted binary search.

Do not generate a large direct `max_field + 1` table for sparse schemas.

## Generic loop

The generic loop keeps the current semantic order:

1. decode tag with the existing `decode_tag` semantics;
2. find a table entry by field number;
3. if no entry or wire mismatch, capture/skip unknown using existing helpers;
4. call a small safe handler for the `FieldKind`;
5. enforce last-wins, oneof replacement, proto2 required checks, UTF-8 mode,
   unknown enum retention, recursion limit, groups, and packed/unpacked
   compatibility exactly as generated `merge_inner` does today.

Handlers should reuse existing runtime helpers:

- `decode_varint`, `read_fixed32`, `read_fixed64`, `read_len_span`;
- `LazyStr::from_parse_span`, `LazyBytes::from_parse_span`;
- `Packed::*::append_wire` / validation;
- map entry decode helpers generated per concrete map type.

The initial table-driven parser should remain safe Rust. If later profiling
justifies raw field offsets, that is a separate implementation card requiring:

- one local `unsafe` abstraction for offset writes;
- `SAFETY` comments at every use;
- a new `docs/unsafe-invariants.md` entry;
- Miri coverage for table handlers and representative generated messages.

## Selection heuristic

Generate inline parse when all are true:

- `field_count <= 8`;
- no maps;
- no groups;
- no proto2 required fields;
- no more than one repeated string/bytes/message field;
- generated parse arm source estimate under about 120 lines.

Generate table-driven parse when any are true:

- `field_count >= 16`;
- has maps or multiple repeated fields;
- has several lazy submessages or packed fields;
- parse-arm source estimate exceeds about 240 lines;
- SB-09/codegen-matrix shows the message contributes materially to generated
  Rust bytes or clean-check time.

Messages in the middle keep inline parsing until dev-loop evidence proves a
benefit. The threshold is intentionally conservative because PK-04 and the
small-shape measurements show tiny-message overhead can be dominated by a few
instructions.

## Code-size and compile-time budget

The implementation target is:

- reduce generated Rust bytes for wide messages by at least 15%;
- reduce clean `cargo check` time on SB-09 100/1,000-message corpora or keep it
  within noise while improving parse instructions;
- no more than +5% generated bytes for small inline-selected messages;
- no public API changes.

GN-01 `docs/evidence/compile-cost.md` is not present in this worktree yet.
When it lands, PK-05/PK-06 must cite its top compile-cost rows. Expected
compile-cost reductions come from replacing many monomorphic `match` arms and
duplicated map/repeated validation snippets with shared runtime handlers plus
compact constants. Expected costs are extra static data and a generic dispatch
function; the heuristic keeps those costs away from tiny messages.

## Performance hypotheses and rollback criteria

Target cells:

- `codec.pbrs.owned_decode` and `codec.pbrs.parse_touch`;
- new shape cells: `packed_256`, `unpacked_256`, `tags_32`;
- SB-09/codegen corpora once available for code size/check/build costs.

Hypotheses:

1. Wide/cold messages improve instruction count by reducing generated branch
   footprint and instruction-cache pressure.
2. Small hot messages are best left inline; table dispatch should not run for
   `empty`, `id`, `name_80`, or similar common tiny shapes until measured.
3. Compile time improves on large generated corpora by replacing repeated parse
   arm source with shared code.

Rollback criteria:

- any primary codec cell regresses by >1% instructions without an allocation or
  copy-count win;
- conformance is not 100%;
- generated compatibility fixtures fail to build;
- generated bytes increase on 100/1,000-message corpora without a matching
  parse-speed win.

## Compatibility with UK kernel work

The pbrs table uses protobuf concepts rather than generated Rust field names:
field number, wire type, cardinality, presence, oneof, storage slot, and field
kind. UK-18 can later map these entries to official `rust_out`/MiniTable
concepts. This card does not wait on the UK kernel, and it must not change the
existing `src/runtime.rs` MiniTable ABI.

## Validation plan for implementation cards

Required gates:

- targeted dev-loop Linux instruction comparisons via `scripts/devloop-linux.sh`;
- `cargo test -p pbrs --lib`;
- generated codegen-compat fixtures;
- `./scripts/conformance.sh`;
- fuzz target build plus parser differential fuzzing for table-vs-inline paths;
- Miri only if a later implementation introduces unsafe offsets.
