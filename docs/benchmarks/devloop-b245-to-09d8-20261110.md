# Dev-loop advisory comparison, November 10

The [dev-loop run](https://github.com/mingley/pure-protobuf/actions/runs/42748958698)
compared base `b245104850f4e269e236bf54482d20d59e0db18c` with head
`09d8ad6b0b1ee4fec15fe14f2521d0031fa41997`. Both measurements and evidence
validation succeeded, with 1,634 common cells and none added or removed.
The workflow passed, but its comparison exited **1** and is advisory. Hardware
instruction counts were unavailable (`not_run`); this run does not establish
a CPU-speed, latency or overall ranking.

The comparator reported 622 threshold-exceeding metric rows: 247 syscall, 374
`locks` proxy and one allocation-byte row. It also printed 613 improvements
(251 syscall and 362 `locks` proxy rows) and eight additional absolute
`locks` budget overruns. These are metric rows, not unique benchmark cells
or wins against tonic. All 1,243 printed rows cover 792 distinct cells. The
[retained JSON](devloop-b245-to-09d8-20261110.json) preserves each printed row
in order; the original artifact contains both complete reports and logs.

The eight overrun cells are `pick_first`, `round_robin`,
`weighted_round_robin`, `ring_hash`, `least_request`, `priority`,
`outlier_detection` and `random_subsetting_experimental`. Each reported
0.0005 against a zero `locks` budget. The `locks` field is a process-wide
`strace` count of futex calls, including setup, wakes and unsuccessful waits;
it is not a count of lock acquisitions. These shared-runner proxy observations
need investigation and do not establish their cause or application impact.

The allocation-byte threshold row is
`rpc.tonic_transport.reference_reference.entities.n1000.server_stream`.
Its reported median changed from 193,984.990 to 193,987.430 allocations and
28,953,700.75 to 30,012,750.325 requested bytes per RPC (+3.66% bytes, versus
a 2% limit). This fixture uses the reference tonic client and server. Its
allocation counts varied across repeats; the observation is not a proven
effect of the source change.

## Selected allocation cells

These are specific fixtures from the same report, not a CPU benchmark. Query
`d4.v6` is depth 4, variant 6. Codec rows report allocations and requested
bytes per operation as exact; RPC rows are medians per RPC and include work by
both client and server in one process. The table shows the head revision; all
selected values also matched the base in this run.

| Operation or RPC profile | Allocations | Requested bytes |
|---|---:|---:|
| pbrs Query fresh construction and encode | 50.000 | 2,949.0 |
| Prost Query fresh construction and encode | 23.000 | 2,421.0 |
| pbrs Query owned decode | 39.000 | 4,168.0 |
| Prost Query owned decode | 22.000 | 3,942.0 |
| native pbrs unary | 157.000 | 28,988.0 |
| native Prost unary | 87.000 | 26,972.0 |
| tonic pbrs unary | 195.010 | 57,615.68 |
| tonic Prost unary | 125.010 | 54,815.68 |

Fresh encode constructs and drops a fresh message tree as well as encoding it.
Owned decode decodes and drops a message from the common wire. Unary RPCs use
the same schema-qualified input, loopback TCP and two Tokio workers. A
full-value response is validated before warmup; measured responses are read
and checked. The pbrs Query examples request more allocations and bytes than
the corresponding Prost codec examples. Native pbrs requests more allocations
and fewer bytes than tonic Prost in this selected RPC fixture. These results
identify work to investigate; they do not establish a universal ranking.

The counting allocator measures successful allocation and reallocation
requests and requested sizes, not live or peak memory. Instrumentation and
scheduling affect the RPC medians. The run's
[original artifact](https://github.com/mingley/pure-protobuf/actions/runs/42748958698/artifacts/13734563761)
