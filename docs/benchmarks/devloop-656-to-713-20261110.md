`fresh_encode` constructs and drops a fresh message tree as well as encoding
it; EntityList construction also builds and encodes nested `Any` payloads.
`owned_decode` decodes and drops a message from the same borrowed,
Prost-produced wire. `read_all` decodes, walks and drops it.
`fully_read_clone` clones and drops a prepared, fully read message.
Fresh-encode uses independent warmup objects.

## Unary RPC allocations

Each cell is **allocations / requested bytes per RPC**, reported as a median.
Native profiles use the pbrs-grpc client and server; tonic profiles use the
tonic client and server. The suffix chooses the codec.

| Query d4/v6 profile | Allocations / requested bytes |
| --- | ---: |
| `native_pbrs` | 157.015 / 28990.28 |
| `native_prost` | 87.005 / 26972.76 |
| `tonic_pbrs` | 195.010 / 57615.68 |
| `tonic_prost` | 125.010 / 54815.68 |

The clients and servers run in the same process over TCP loopback using two
Tokio workers. Both codec inputs are decoded from the same schema-qualified
wire, fully read, then cloned for each RPC. A response receives full decoded
value validation before warmup; measured responses are fully read and checked
against a checksum. Process-wide counts include both endpoints. Allocator
instrumentation can affect execution.

The Query codec cells use more pbrs allocations and requested bytes than Prost
in these four operations. Fresh EntityList construction plus encoding also uses
more of both; owned decode uses fewer allocations but more requested bytes,
while read-all and clone use less of both. The native pbrs RPC uses more
allocations and fewer requested bytes than the tonic Prost RPC in this run.
These selected cells identify work to investigate; they do not attribute the
differences to a particular change.

## Evidence and limits

The counting allocator records successful allocation and reallocation requests
and requested sizes, including the new size of reallocations. Requested bytes
are not retained, live or peak memory. RPC counts are medians and can vary
with scheduling; codec counts in these tables are reported exact by the
harness. The workflow uses shared infrastructure and the selected cells do not
cover all fixtures, workloads or implementations.
