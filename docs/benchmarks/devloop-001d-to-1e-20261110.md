## Codec allocations

Each cell is **allocations / requested bytes per operation**, reported exact by the harness. `query.d4.v6` uses the Query fixture with depth 4 and variant 6; `entities.n1000` uses an EntityList with 1,000 records.

| Query operation | pbrs | Prost |
| --- | ---: | ---: |
| `fresh_encode` | 50.000 / 2949.0 | 23.000 / 2421.0 |
| `owned_decode` | 39.000 / 4168.0 | 22.000 / 3942.0 |
| `read_all` | 47.000 / 4868.0 | 22.000 / 3942.0 |
| `fully_read_clone` | 39.000 / 2340.0 | 21.000 / 1182.0 |

| EntityList operation | pbrs | Prost |
| --- | ---: | ---: |
| `fresh_encode` | 38002.000 / 2899166.0 | 27335.000 / 2096502.0 |
| `owned_decode` | 13668.000 / 2081520.0 | 18342.000 / 2032926.0 |
| `read_all` | 17668.000 / 2705520.0 | 22342.000 / 2791410.0 |
| `fully_read_clone` | 12668.000 / 850664.0 | 17334.000 / 1011294.0 |

`fresh_encode` constructs and drops a fresh message tree as well as encoding it; the EntityList construction also builds and encodes nested Any payloads. It is not an encode-only measurement. `owned_decode` decodes and drops a message from the same borrowed, Prost-produced wire. `read_all` decodes, walks, and drops it. `fully_read_clone` clones and drops a prepared message that was already fully read. Fresh-encode uses independent warmup objects.

## Unary RPC allocations

Each cell is **allocations / requested bytes per RPC**, reported as a median. The native profiles use the pbrs-grpc client and server; the tonic profiles use the tonic client and server. The suffix chooses the codec.

| Query d4/v6 profile | Allocations / requested bytes |
| --- | ---: |
| `native_pbrs` | 157.000 / 28988.0 |
| `native_prost` | 87.045 / 26978.84 |
| `tonic_pbrs` | 195.010 / 57615.68 |
| `tonic_prost` | 125.010 / 54815.68 |

The clients and servers run in the same process over TCP loopback using two Tokio workers. Both codec inputs are decoded from the same schema-qualified wire, fully read, then cloned for each RPC. A response receives full decoded-value validation before warmup; measured responses are fully read and checked against a checksum. Counts cover the process-wide measurement window, so they include client and server work. Allocator instrumentation can affect execution.

The Query codec cells show more pbrs allocations and requested bytes than Prost in these four selected operations. For the EntityList, fresh construction plus encoding has more of both; owned decode has fewer allocations but more requested bytes, and read-all and clone have less of both. The native pbrs RPC uses more allocations and fewer requested bytes than the tonic Prost RPC in this run. These observations identify specific cells for investigation; they do not attribute the differences to a particular change.

## Evidence and limits

The counting allocator records successful allocation and reallocation requests and requested sizes, including the new size of reallocations. Requested bytes are not retained, live, or peak memory. RPC counts are medians and may vary with scheduling; codec counts in these tables are reported exact by the harness. The workflow runs on shared infrastructure. The selected cells do not cover all fixtures, workloads, or implementations.
